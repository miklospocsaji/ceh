# M3.5 Owner commands and resuming work items

Settled by the owner on 15 November 2026. Brief section 7 points here. The decisions go to brief section 8 and an ADR when the first change, `add-owner-commands`, starts.

## 1. Why

- In M3 the factory ignores every issue comment except `/approve`, and its roles read only the issue's title and body. The owner's answers to a proposal's open questions, and any other feedback, reach the factory only by editing the issue body. Design and Plan see that edit, but the proposal already written never does.
- The owner cannot ask the factory why a proposal or design says what it says, short of reading the branch and guessing.
- A work item whose execution was stopped or failed cannot be resumed. Relabelling the issue starts an execution whose Intake answers `duplicate`, and the only way on is a new issue that repeats Intake, Proposal, the approval, Design and Plan. This happened in M3's exit run with #11.
- The owner cannot stop a work item from the issue, or ask where it stands, without the AWS console.

## 2. How a comment reaches the factory (settled)

A comment is for the factory only if its first line is a command, and only the owner's commands count.

- A command is a first line of the form `/<verb>`, optionally followed by more text on that line and on the following lines. Leading and trailing whitespace on the first line is ignored. The verb is lowercase.
- Everything else is ignored and gets no reply: comments without a command, comments where the command is not on the first line (a command quoted in the middle of a discussion stays inert), and every non-owner's comment, even one with a command. Non-owner commands show only in the webhook log, as today. A reply to a non-owner would let anyone make the bot post.
- The owner is `owner` in `targets/<name>/target.yaml`, as for `/approve` today.

Alternatives considered:

| Option | For | Against |
| --- | --- | --- |
| **First-line slash command (chosen)** | Already how `/approve` works; deliberate, easy to type, and teammates' comments can't trigger it by accident; the webhook decides without the ledger | Collides only if another bot on the same repository uses the same verb |
| Mention `@ceh-app` | Reads naturally | GitHub App bot accounts (`ceh-app[bot]`) are not reliably mentionable or autocompleted; a mention in passing would count as a command |
| Namespaced, e.g. `/ceh revise` | No collision with other bots | Longer to type, and there is no other bot today. Can be added later as a per-target option without breaking `/<verb>` |
| Any owner comment is feedback | Nothing to learn | The owner cannot talk to teammates on the issue; a stray "thanks" would re-run a role |

## 3. Commands

| Command | Text after the verb | Valid when | Effect |
| --- | --- | --- | --- |
| `/approve` | ignored | a proposal or design awaits approval | As today: the execution goes on |
| `/revise` | **required**: answers to open questions and/or requested changes | a proposal or design awaits approval | The author of what awaits runs again with the comment, then the approval is asked again (section 4) |
| `/question` | **required**: the question | a proposal or design awaits approval | The author of what awaits answers in a read-only session; nothing changes, and the approval stays open (section 5) |
| `/abort` | optional reason | the work item's execution is running | Stops the execution; the work item becomes `aborted`. It can be resumed |
| `/resume` | optional guidance for the role that runs next | the work item's execution has ended (`aborted`, `escalated`, or failed/stopped outside the factory), the issue is open, and the PR is not open yet | A new execution continues the work item from where it stopped (section 7) |
| `/status` | ignored | always | Replies with the state, the step, task progress, attempts, cost so far and what the factory waits for |
| `/help` | ignored | always | Replies with this table, short |

Every owner command gets exactly one reply comment, saying what was done or why nothing was done. An unknown verb gets "unknown command" and the `/help` text, so a typo never passes silently. A `/revise` or `/question` without text is refused with a reply.

Every command is recorded in the ledger. `/approve`, `/revise`, `/abort` and `/resume` count as owner interventions, for the "interventions per work item" metric. `/question`, `/status` and `/help` are recorded but do not count as interventions, since they change nothing.

`/restart` (send an approved proposal back for revision after the approval) is left out of M3.5 (owner, 15 November 2026). Until it exists, the owner `/abort`s and opens a new issue.

## 4. Revising a proposal or a design (settled)

```
Proposal ─▶ AwaitApproval ─┬─ /approve ─▶ Approved ─▶ …
   ▲                       └─ /revise ──┐
   └────────────────────────────────────┘
Design ─▶ (large) AwaitDesignApproval ─┬─ /approve ─▶ Plan
   ▲                                   └─ /revise ──┐
   └────────────────────────────────────────────────┘
```

- The awaiting task's token is resumed with `{ "decision": "revise" }` instead of `{}`, and a Choice after AwaitApproval (AwaitDesignApproval) sends the execution back to Proposal (Design) in the same execution. The approval is closed with the outcome `revise`. The execution history carries only the decision; the comment's text is in the ledger.
- The author runs again on the branch head, so the owner's own edits on the branch are kept. Its input is:
  - the issue
  - the current change files
  - **all** the owner's applied `/revise` comments for that stage, oldest first
  - the stage's `/question`s and their answers, so a `/revise` can refer to an answer ("do what you suggested")

  Its prompt says to answer what was asked, change only what the feedback touches, and move answered open questions out of the open questions. A new commit follows. The summary comment is posted again with a short "what changed" from the author's result, then the approval is asked again.
- Only the role being revised sees the comments (proposal author for the proposal, architect for the design). Later roles see only the artifacts (principle 4), so whatever the owner asks has to land in `proposal.md`, the delta specs or `design.md`.
- A revised proposal can change `x-complexity`; Approved routes on the new value.
- Revising re-runs the role as a new attempt of the same state (`n` goes on), and its cost counts toward the work item's budget.
- At most 5 revisions per stage. The 6th `/revise` is refused with a reply that suggests a new issue. The $5 per-work-item budget applies anyway.
- A `medium` design has no owner approval (the design reviewer decides). The owner can still `/abort` it.

The summary comment ends with the commands that apply: "Reply `/approve`, `/revise` with your answers or the changes you want, or `/question` to ask about it."

## 5. Asking a question (settled)

`/question <text>` asks the author of what awaits approval about it: the proposal author for a proposal, the architect for a large design. It is valid only while a proposal or design awaits approval. At any other time it gets the busy reply (while a role runs) or "nothing awaits" (otherwise), like `/revise`.

How it works:

- **No state machine change.** The execution stays paused in its `waitForTaskToken` state, and the approval stays open with its token untouched. The `command` worker task runs the answering session itself and posts the answer, so `/approve` or `/revise` keep working exactly as before the question.
- **Read-only by construction, not by prompt.** The answer runs the role's model and prompt with a question overlay, but with the tools `Read`, `Grep` and `Glob` only, no writable paths, no `WebFetch`, and structured output `{ answer }`. It works on a fresh clone of the branch head and never commits or pushes. Even if the question says "fix it", the session cannot change anything. Its prompt says to point to `/revise` when the question asks for a change.
- **A fresh session, not the author's memory.** Roles keep no transcripts (principle 4), so "why did you choose X?" is answered from the artifacts, the issue, the specs and the code, as a new colleague would. The answer says so when the artifacts do not record a reason. This is the honest limit of `/question`. It improves if the authors' prompts ask them to record their reasons, which is worth doing anyway.
- **Input:** the issue, the change files at the branch head (whose commit SHA the answer names), the stage's `/revise` comments, earlier questions and answers of the stage, and the new question.
- **Limits:** a small turn cap (10) and budget ($0.30 per answer), counting toward the work item's budget, and at most 10 questions per stage. One question at a time per work item: a `/question` while another is being answered gets the busy reply.
- **Approval or revision during a question:** a question is not a lock. An `/approve` or `/revise` that arrives while the answer is being written goes through at once. The answer is still posted, naming the commit it read, so an answer to a proposal that has since been revised is visibly about the old one.
- **Ledger:** an attempt in state `proposal-question` or `design-question`, linked to the question's comment, with `{ answer }` as its result and the usual messages and cost.

Thoughts and alternatives:

| Option | For | Against |
| --- | --- | --- |
| **Answer in the `command` task, execution untouched (chosen)** | No state machine change, and approvals are never blocked or put at risk | The answer runs outside Step Functions, so it gets no Step Functions retry. A crashed answer is a failed attempt, and the owner asks again |
| Route through the state machine (resume the token with `question`, answer, then wait again) | Every role run is in the execution history | Each question needs a new task token and a re-posted approval prompt; a crash mid-answer could leave the work item without an open approval |
| Let `/revise` carry questions too ("answer, don't change") | No new command | Mixes a change and a non-change in one command; the author would be allowed to write while asked not to |

Not in scope: questions while a role runs, or about an escalated or aborted work item ("why did the build fail?"). Those would be answered from failure evidence by a different role, and may come with M6's console.

## 6. What a comment means in each state (settled)

Requirement from the owner: comments that arrive while a role writes or rewrites are not queued, and the bot says so.

| Work item state | `/approve` | `/revise`, `/question` | `/abort` | `/resume` | `/status`, `/help` |
| --- | --- | --- | --- | --- | --- |
| no work item on the issue | "nothing awaits" | "nothing awaits" | "nothing runs" | "no work item; label the issue `factory`" | reply |
| `intake`, `proposal` (writing or revising) | busy reply* | busy reply* | stops | "running" | reply |
| `awaiting-proposal-approval` | approves | revises / answers | stops | "running" | reply |
| `proposal-approved`, `design`, `design-review`, `plan` | busy reply* | busy reply* | stops | "running" | reply |
| `awaiting-design-approval` | approves | revises / answers | stops | "running" | reply |
| `build` | "nothing awaits" | "nothing awaits; `/abort`, or a new issue" | stops | "running" | reply |
| `aborted`, `escalated` | "nothing awaits; `/resume`" | "nothing awaits; `/resume`" | "nothing runs" | resumes | reply |
| `pr-open` | "the PR is open; review it" | same | "nothing runs" | "the PR is open" | reply |

\* busy reply: "`<step>` is running, so your `/<verb>` was not applied and is not kept. Send it again when the factory asks for your approval." The reply quotes the first line, so the owner sees which comment it means.

Comments on the pull request are out of scope; review comments belong to M4's reviewer.

## 7. Resuming (settled)

- **Trigger:** `/resume` only. Relabelling a work item's issue still ends in a `duplicate` Intake, whose comment now says "use `/resume`". Relabelling stays the way to start, and `/resume` the way to continue.
- **Who starts it:** the `command` worker task (section 9), which checks that the work item may resume and that its execution has ended (`states:DescribeExecution`). Then it starts a new execution, named `issue-<n>-resume-<comment id>`, with input `{ issueNumber, resume: true }`. Intake adopts the work item: it stores the new execution ARN and answers which state to enter. A Choice at the start of the state machine routes there.
- **Where it enters:** from the work item's state, or for `aborted`/`escalated` from `stopped_in`, a new column that records the state the work item was in when it stopped:
  - `intake`, `proposal` → Proposal (the open attempt is closed `aborted`, and the role runs again)
  - `awaiting-proposal-approval` → AwaitApproval: a new token and the summary posted again. No second `/approve` is asked for anything already approved, because an approved work item is past this state
  - `proposal-approved` → Approved; `design`, `design-review` → Design or DesignReview; `awaiting-design-approval` → AwaitDesignApproval; `plan` → Plan
  - `build` → BuildTasks with the tasks from the ledger. Step skips a task that is ticked in `tasks.md` and done in the ledger, so finished tasks are not rebuilt
- **Idempotency:** every state already refuses a work item in the wrong state (`NotApplicable`). Each entry state above must accept the work item in its own state, as Approved already does. That is the main implementation work.
- **Open attempts and counts:** stopping closes the open attempt with the new outcome `aborted`, which never counts toward a retry limit (bug, infra or crash). After an escalation, `/resume` gives the escalated state a fresh set of retries. The `/resume` text, if any, goes to the next role as owner guidance next to the failure evidence. This is the answer to a `spec-ambiguity` escalation.
- **Escalated work items:** may be resumed. The evidence is the ledger's last failed attempt (as for a retry) plus the owner's `/resume` text.
- **Aborted means paused, not final.** To end a work item for good, the owner closes the issue: `issues.closed` aborts a running execution, and `/resume` on a closed issue is refused. Reopening the issue makes `/resume` work again.

## 8. Ledger

One migration per change (section 10), together:

- `comments`: work item (nullable), GitHub comment id (unique, so a webhook redelivery is a no-op), author, verb, body, received at, outcome (`applied`, `busy`, `refused`, `unknown`), and the work item state it met. The body is stored at receipt, so later edits or deletes on GitHub change nothing, and a replay sees what the role saw.
- `work_items.state` gains `aborted`; new column `stopped_in`.
- `attempts.outcome` gains `aborted`; attempts get `comment_ids` (the `/revise`, `/question` or `/resume` comments the role was given).
- `approvals` gain an outcome: `approved`, `revise` or `aborted`.

## 9. Mechanics

- **Webhook** (still no ledger, no GitHub token): for `issue_comment.created` on an issue of the target by the owner whose first line starts with `/`, one RunTask of `factory-worker command --issue <n> --comment <comment id>`. It replaces today's `approve` task. The webhook passes only the comment id, never the text (RunTask overrides are limited to 8 KB, and principle: pointers only). `issues.closed` → `command --issue <n> --closed`.
- **`command` worker task:** reads the comment through the Forge by id, parses the verb, records it, and decides under a per-work-item lock (`SELECT … FOR UPDATE` on the work item), so `/revise` and `/abort` arriving together are applied in order. The lock covers the decision and the ledger writes, never a role session: a `/question` marks itself in progress and releases the lock before it runs. Then the task replies. The worker task takes about a minute to start on Fargate, so replies come in about a minute.
- **Stopping:** `StopExecution` on the work item's execution. For `.sync` ECS tasks, Step Functions stops the running ECS task. The first task of the resume change is a spike to check that for both the worker and the build task. Open approvals are closed `aborted`.
- **IAM:** the worker gets `states:StopExecution`, `states:DescribeExecution` and `states:StartExecution` on its own state machine and its executions only.
- **Comments are data, not instructions:** they reach roles inside a delimited block, the role prompts say they are the owner's feedback on the artifact, and the path guards and tool allowlists apply whatever the text says. Only the owner's comments are ever stored as input.
- **Edited comments:** `issue_comment.edited` is ignored. To change a command, the owner writes a new comment.
- **Local runs:** `pnpm factory command --issue <n> --comment <id>` runs the same handler against the local ledger, so a local run that stopped at an approval can be revised or questioned, with `pnpm factory run` going on from there. `pnpm factory approve` stays as a shortcut.

## 10. Delivery: three OpenSpec changes (settled)

One change would carry too much: a new worker entry point and webhook route, a state machine loop, two new role modes, resumable entry for every state, stopping executions, and new IAM. That is more than one design can review well, and more than one local session can build and check. The brief's convention is scope per milestone, not one change per milestone; M3 shipped as several changes. All three are archived when M3.5 exits.

1. **`add-owner-commands`**: the foundation, useful on its own.
   - The webhook's route for owner commands, and the `command` worker task replacing `approve` (`/approve` moves onto it unchanged).
   - The `comments` table, `/status`, `/help`, the unknown-command and busy replies, and the state table of section 6, with `/revise`, `/question`, `/abort` and `/resume` answered "not yet available" until their changes land.
   - The local `pnpm factory command`.
   - Proves: a non-command and a non-owner command produce nothing, and `/status` answers in the cloud.
2. **`add-approval-feedback`**: `/revise` and `/question` while a proposal or design awaits approval.
   - The decision output and Choices after both approval waits, the revision inputs and limits, and the approval outcomes.
   - The read-only question mode of the proposal author and the architect, and the updated summary comment.
3. **`add-work-item-resume`**: `/abort`, `/resume`, and the closed issue.
   - `aborted` and `stopped_in`, the `aborted` attempt outcome, the stop spike, and the IAM.
   - Intake adopting a work item, the start Choice, and every entry state accepting a work item in its own state.

Changes 2 and 3 both build on 1 and not on each other. They are built in the order above, 2 before 3, since 2 is what the owner meets on every work item.

## 11. Exit

On a fresh `vocab` issue, in the cloud, after all three changes:

1. The proposal asks at least one open question. The owner asks a `/question` about the proposal and gets an answer, with the approval still open. Then the owner answers the open question with `/revise`, and the revised proposal reflects the answer and no longer lists the question.
2. A `/revise` sent while the proposal is being rewritten gets the busy reply and changes nothing.
3. A teammate-style owner comment with no command, and a `/approve` from another account, produce no reply and no task.
4. `/status` answers in each of: awaiting approval, Build.
5. The owner `/abort`s during Build and `/resume`s. The work item reaches a pull request opened by `ceh-app[bot]`, with no task rebuilt that was done before the abort and no second `/approve`.

The design revision and design questions (large changes only), and the issue-closed path, are proved by unit tests against `FakeForge` and the local ledger, and by `pnpm test:cloud` where they touch AWS. The exit run does not have to force a `large` change.

## 12. Decisions

All settled by the owner on 15 November 2026:

- [x] Commands are first-line `/<verb>`, owner only; everything else is ignored silently (section 2).
- [x] One `/revise` for both answers and change requests, rather than a separate `/answer`.
- [x] Commands that arrive while a role runs are refused with a busy reply, never queued (section 6).
- [x] At most 5 revisions per stage.
- [x] `/abort` pauses (resumable); closing the issue is the final stop.
- [x] `/resume` only, not relabelling; resuming an escalated work item resets its retry counts.
- [x] `/restart` is left out of M3.5.
- [x] `/question` as in section 5: answered in the `command` task by a read-only session of the awaiting stage's author, with 10 questions per stage, $0.30 and 10 turns per answer.
- [x] Three changes, in the order of section 10: `add-owner-commands`, `add-approval-feedback`, `add-work-item-resume`.
